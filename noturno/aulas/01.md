# Origem: Controle de Versão, Problemas Históricos e Criação do Git

Software não é produzido de uma vez, em uma única escrita. Um projeto é alterado para corrigir defeitos, adicionar recursos, trocar regras, atualizar dependências, testar alternativas e desfazer decisões.

Um sistema de controle de versão (Version Control System, VCS) registra mudanças em arquivos ao longo do tempo para que versões específicas possam ser recuperadas depois.

## O Método Histórico

Antes de um VCS, a solução era fazer cópias:

```
projeto/
projeto_backup/
projeto_final/
projeto_final_agora_vai/
projeto_final_agora_vai_2/
```

Tem problema fazer assim?

| PROBLEMA | CONSEQUÊNCIA |
| -------- | ------------ |
| nomes de pastas não são a estrutura da história | ninguém sabe qual versão é a correta |
| a cópia (manual) depende de memória | mudanças podem ser perdidas ou duplicadas |
| comparação é difícil | precisa inspecionar muito para descobrir o que mudou |
| não há autoria confiável | não há como sabem quem alterou nem com qual intenção |
| colaboração sobreescreve arquivos | uma pessoa pode apagar o trabalho de outra |
| rollback é impreciso | restaurar uma cópia pode descartar mudanças importantes |

## Funções de um VCS

| Pergunta | Resposta |
| -------- | -------- |
| O que mudou? | diferença entre dois estados |
| Quando mudou? | data e ordem dos registros |
| Quem mudou? | autor e registro da alteração |
| Por que mudou? | mensagem, issue, revisão ou documentação |
| Como voltar? | recuperação de arquivo, conjunto de arquivos ou tudo |
| Posso testar algo sem quebrar tudo? | linha paralela de desenvolvimento |
| Como integrar trabalho simultâneo? | comparação, merge e resolução explícita de conflitos |

Controle de versão não evita error. Ele transforma erros em eventos visíveis, comparáveis e, muitas vezes, reversíveis.

## As Três Gerações de Sistemas de Versão

No VCS, há um projeto e há um histórico das alterações do projeto.

No modelo mais simples, esse histórico está na mesma máquina:

PC da Jess

┌──────────────────────────┐
│ projeto                  │
│                          │
│  arquivo.c               │
│  main.c                  │
│  README.md               │
│                          │
├──────────────────────────┤
│ histórico                │
│                          │
│  versão 1                │
│  versão 2                │
│  versão 3                │
└──────────────────────────┘

Eu, Jess (ooiiiii), consigo voltar pra outras versões, comparar elas, etc.
Mas, e se o Eduardo, Dudz (dá oi), também quer trabalhar no projeto?

### Controle Local

Os sistemas locais mantinham um banco de revisões na própria máquina.

```
PC da Jess
├── arquivo/projeto
└── histórico
```

Dudz não tem acesso to histórico.

Se Jess quiser passar o projeto pro Dudz, dá pra copiar os arquivos e mandar!

```
Jess ──────→ Dudz
        projeto
```

Se ambos trabalharem no projeto:

```
Jess               Dudz

A ── B ── C        A ── X ── Y
```

Há duas histórias diferentes.

Como juntar `C` com `Y`?

### Controle Centralizado

Uma solução é colocar o projeto e o histórico em uma máquina acessível para todos.

```
                 servidor
              ┌─────────────┐
              │   projeto   │
              │  histórico  │
              └─────────────┘
                ↑    ↑    ↑
                │    │    │
               Jess  Dudz Kauan
```
